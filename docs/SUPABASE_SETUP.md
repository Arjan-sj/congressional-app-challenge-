# SafeRoutes — Supabase setup (pilot MVP)

This file accompanies `supabase/migrations/202610180001_initial_schema.sql`.

## What is and is not set up

- ✅ Database schema and conservative access-policy SQL are prepared in GitHub.
- ⏳ You must **create/connect a Supabase project and run the migration**. No remote database has been created by this commit.
- ✅ Flutter reads RLS-visible reports and submits authenticated reports through `supabase_flutter`.
- ⏳ You must provide the project URL and publishable key through `--dart-define`; without them, reporting is disabled.

## 1. Create a Supabase project

1. Visit https://supabase.com/dashboard and sign in or sign up.
2. Choose **New project**. Project name: `saferoutes` (or your preferred name).
3. Select your organization and a nearby region; choose a strong database password. **Do not share this password or paste it into ChatGPT.**
4. Wait until the database is ready. The account owner should add the other developer through the project's access/invite settings.
5. Optionally install/connect the Supabase app in ChatGPT if you want database assistance directly through ChatGPT.

## 2. Apply the migration once

1. Supabase Dashboard → **SQL Editor** → **New query**.
2. Open `supabase/migrations/202610180001_initial_schema.sql` from GitHub.
3. Copy all of its SQL into the editor; verify you have selected your new development project.
4. Click **Run** and confirm completion.
5. Table Editor should show `public.schools` and `public.hazard_reports`.

**Important:** SQL Editor runs with elevated privileges and is NOT an RLS test. Do not expose this SQL Editor to the public.

## 3. Review security before adding Flutter

- The `schools` table is publicly readable but only a trusted admin can change it.
- Only signed-in users can submit reports. All client inserts MUST be `unverified`.
- Public users see only `verified` and `resolved` hazard reports; the author may view their own pending reports after signing in.
- No client may directly update/delete or verify reports.
- **Moderator workflow is NOT implemented.** Don't claim submitted reports are reviewed until you build one.
- Keep photo uploads off until storage policies and privacy controls exist.

## 4. Credentials you will eventually use in Flutter

Open Supabase → **Connect** or **Project Settings → API** (menu labels may vary):
- **Project URL:** `https://YOUR_PROJECT_REF.supabase.co`
- **Publishable key:** the key intended for browser/mobile clients.

Never add a `service_role`, secret key, database password, or personal access token to GitHub, screenshots, Flutter code, or chat messages.

The publishable key is visible in a web app; the security comes from Row Level Security (RLS) and minimal grants, **not** hiding that key.

## 5. Mapping between Dart and SQL

| Dart model | SQL column/value |
| --- | --- |
| `schoolId` | `school_id` (`sample-school`) |
| `createdAt` | `created_at` (generated by database) |
| `isDemo` | `is_demo` |
| `status` | `status`, default `unverified` |
| `missingSidewalk` | `missing_sidewalk` |
| `difficultCrossing` | `difficult_crossing` |
| `blockedPath` | `blocked_path` |
| `bikeRoute` | `bike_route` |

The Flutter client must convert enum values to these SQL strings, and must supply a map-selected latitude/longitude when inserting. It should not transmit a trusted `status` or `reporter_id`.

## 7. Safety notes

- Never gather children's names, home addresses, recurring routes, or commute schedules.
- Sample school coordinates are approximate. They do not identify a verified pedestrian entrance.
- Hazard severity is **self-reported**, not a measured collision probability.
- A map marker is not proof of danger; distinguish unverified and reviewed information.
- Before production, implement abuse/rate limiting, retention rules, and proper public-data review.
